# SPMD Dialect

An MLIR dialect and toolchain for statically verifying or optimizing SPMD (single-program,
multiple-data) parallel programs — data races, collective-communication
mismatches, and thread-safety violations and more — across multiple programming
models (MPI, OpenSHMEM, NVSHMEM, NCCL, CUDA, OpenMP).

## Build system

Bazel, not CMake. There is no `BUILD`-free path — LLVM/MLIR, Enzyme, Enzyme-JAX
and Reactant are pulled in (or overridden to local checkouts) via
`workspace.bzl` / `.bazelrc`, so plain `clang++`/`cmake` invocations against
this tree won't work.

Load modules first (see repo README for the exact versions — GCCcore, LLVM,
CUDA, CMake, Ninja, Python, Bazel), then:

```sh
export CC=clang CXX=clang++
bazel --output_base=/tmp/$USER/bazelOut build -c opt --spawn_strategy=local //utility:spmd-verify
```

- `--output_base=` avoids HPC home-directory disk-quota/file-count limits — always pass it on HPC clusters (CLAIX included).
- `--spawn_strategy=local` for faster builds here.
- Build targets land in `bazel-bin/` (symlink into `bazel-out/`).
- `-c opt` vs `-c dbg` for release/debug. `--config=dev_opt` or `--copt=-UNDEBUG` re-enables debug functionality (e.g. dump methods) in an otherwise release build.
- Building this way also builds LLVM/MLIR/Enzyme/Enzyme-JAX/Reactant from source — first build is long even with local mode (~6 min for spmd itself on 96 cores once deps are cached; the dependency build is the expensive part).
- On shared/HPC login nodes: pass `-j #procs` (ninja) or `--local_resources=cpu=#procs` / `--local_resources=memory=#MB` (bazel) — auto-probing of "available" hardware ignores per-user process/RAM limits and can hang.

Key targets:
- `//utility:spmd-verify` — the main wrapper script (source-to-verification pipeline); also builds `spmd-opt`.
- `//spmd-opt:spmd-opt` — the MLIR opt tool if you only need pass execution.

For local iteration on Enzyme-JAX/Enzyme, set `OVERRIDE_ENZYME_JAX_PATH` / `OVERRIDE_ENZYME_PATH` in `workspace.bzl` (and Enzyme-JAX's own `workspace.bzl`) to point at sibling checkouts instead of pinned commits — a workspace-level `../CLAUDE.md`, where the checkout has one (it is not part of this repository), describes how those sibling repos are laid out.

## Running verification

`spmd-verify` is the primary entry point (compiles source → MLIR → runs a check pass):

```sh
bazel-bin/utility/spmd-verify check-dataRace emitSPMDIR path/to/file.c
```

Verification passes: `check-dataRace`, `check-collectives` (accepts a rank
count), `check-thread-safety`. See `utility/spmd-verify.sh` header comment
for the full flag list (`emitMLIR`, `emitSPMDIR`, `emitJson`,
`printDebugInfo`, `acceptMLIR`, `useOpt`, `noOMP`, `time`, ...).

The `api.json` files are **generated by USIS**
(https://github.com/RWTH-HPC/USIS, conventionally cloned beside `spmd/`) from
each model's own standard/headers and copied in verbatim — never hand-edited.
`includesProgramModels/README.md` has the refresh procedure, the eight fields
CACTS actually reads, and `SPMD_CHECK_API_COVERAGE=1` for checking that every
mapped call still resolves (a miss is otherwise silent).

To run passes directly via `spmd-opt` (bypassing the wrapper), the API
description JSON files must be pointed to manually:

```sh
export PROG_MODEL_INCLUDES=/path/to/spmd/includesProgramModels
export MPI_JSON_PATH="$PROG_MODEL_INCLUDES/mpi/api.json"
export NCCL_JSON_PATH="$PROG_MODEL_INCLUDES/nccl/api.json"
export SHMEM_JSON_PATH="$PROG_MODEL_INCLUDES/shmem/api.json"
export NVSHMEM_JSON_PATH="$PROG_MODEL_INCLUDES/mynvshmem/api.json"
export CUDA_JSON_PATH="$PROG_MODEL_INCLUDES/cuda/api.json"
export OMP_JSON_PATH="$PROG_MODEL_INCLUDES/omp/api.json"

bazel-bin/spmd-opt/spmd-opt -convert-apiCalls-to-spmd input.mlir
```

## Test suites

There are three tiers, with different jobs:

1. **Unit tests** -- hermetic `.mlir` files under `test/spmd/<area>/`, each with
   `RUN: spmd-opt %s -<pass> | FileCheck %s` lines. They need nothing but
   `spmd-opt` and FileCheck, both built by Bazel, and run in CI's `unit-test`
   stage:

   ```sh
   bazel --output_base=/tmp/$USER/bazelOut test -c opt --spawn_strategy=local //test:spmd_tests
   ```

   `test/BUILD.bazel` globs `test/spmd/**/*.mlir` into one `lit_test` per file,
   so a new test needs no BUILD edit; `test/lit.cfg.py` puts the tools on
   `PATH` and unsets `SPMD_IR_EXITCODE` (which would turn a crash into a pass).
   Every new or changed pass gets tests here. `test/spmd/effects/` pins that
   generic MLIR passes (CSE, LICM, control-flow-sink, canonicalize, ...) never
   move, merge or delete communication ops -- update it together with
   `SPMDEffects.td`/`SPMDOps.td` effect declarations.
2. **Benchmark suites** -- end-to-end verification quality on the `externals/`
   corpora through `spmd-verify`, described below.
3. **Execution tests** -- `test/exec/`, self-checking MPI and OpenMP programs
   that `spmd-verify compile` takes through the SPMD dialect and back to a
   binary, run under `mpiexec` (or directly); a wrong value aborts the
   program, and every run is piped into FileCheck for the line saying it
   passed (`PASS <name>`, on rank 0 for the MPI programs). `proxyapps/` does
   the same for whole proxy apps from the race suite's `proxyApps/` (PRK
   MPI-RMA stencil, miniWeather, TeaLeaf), each linked to one bitcode file and
   run on a small input against the app's own validation. They need an
   MPICH-ABI MPI and LLVM's libomp, so they run with plain lit after the Bazel
   build, never through it (loading MPICH for `bazel` changes the action
   environment and rebuilds LLVM):

   ```sh
   ml purge; ml GCC/14.2.0 MPICH/4.3.0 LLVM/20.1.7 CMake/4.0.3
   lit -sv test/exec
   ```

   Without CMake the TeaLeaf test is UNSUPPORTED, and without the submodule
   all of `proxyapps/` is. CI's `roundtrip-exec` job (`apps` stage,
   `allow_failure: true` for now) runs the same. `test/exec/lit.cfg.py`
   documents the substitutions. A program that should also be run after an
   optimisation gets a second `spmd-verify compile opt=<pass>
   intermediates=%t.d` RUN line and a FileCheck (prefix `IR`) over
   `%t.d/02-lowered.mlir` showing the pass did fire.

Submodules under `externals/` must be checked out first:
`git submodule update --init --recursive`.

Two separate CMake build dirs, one per suite/source (conventionally created
as siblings of `spmd/`, i.e. in its parent directory) — `check-collective` and
`check-race`/`check-thread-safety` are targets in *different* CMakeLists, not
three targets of one `cmake -B` (the latter two share one build dir/CMakeLists
since both live in the `data-race-detection-benchmark-suite` submodule —
`check-thread-safety` scopes to its `threadSanityNew/` subtree and runs the
`check-thread-safety` pass instead of `check-dataRace`):

```sh
cmake -B spmdir-coll-tests -S spmd/externals/collective-verification-benchmark-suite -DSPMD_PATH=$PWD/spmd/bazel-bin/utility
LIT_OPTS="-j96" nice -n 10 cmake --build spmdir-coll-tests --target check-collective > results/collectiveResults.log

cmake -B spmdir-race-tests -S spmd/externals/data-race-detection-benchmark-suite -DSPMD_PATH=$PWD/spmd/bazel-bin/utility
LIT_OPTS="-j96" nice -n 10 cmake --build spmdir-race-tests --target check-race > results/raceResults.log
LIT_OPTS="-j96" nice -n 10 cmake --build spmdir-race-tests --target check-thread-safety > results/threadSafetyResults.log
```

(paths above assume cwd = the parent directory of `spmd/`, the workspace root;
adjust `-S`/`SPMD_PATH` if run from elsewhere.) `LIT_OPTS`/`nice` tune
parallelism/priority on shared login nodes — see the per-user resource-limit
note under *Build system* above. Needs the `LLVM` module loaded
(`find_package(LLVM)`) in addition to `CMake`/`Ninja`/`Python` — **and
`CUDA`**: the vendored `nccl.h` is the real upstream header and `#include`s
`cuda_runtime.h`/`cuda_fp16.h`, which only the CUDA module provides
(`includesProgramModels/cuda/include/` is empty). Without it every NCCL test
fails at compile time with `'cuda_runtime.h' file not found` and is scored as a
verification failure — 21 of the 102 collective tests. Load the same set CI
does: `ml GCCcore/14.2.0 LLVM/20.1.7 CUDA/13.1.0 CMake/4.0.3
Ninja/1.12.1 Python/3.13.5`. `useful-scripts/runThreadSanity.sh` (a
workspace-level script, not in this repository) remains a separate ad-hoc
driver over the same `threadSanityNew/` files (TP/FN/TN/FP summary against raw
sources, no lit/XFAIL) — not part of this gate or CI.

**Regression gate: `check-collective`, `check-race`, and `check-thread-safety`
are this project's existing regression suites and should always be run before
committing or pushing.** Re-running `cmake -B` is only needed after
`SPMD_PATH` changes (fresh Bazel output) or the CMake cache goes stale;
otherwise re-run just the `cmake --build ... --target ...` step.

Tests are lit-annotated automatically when building a check target; use the
`annotate-tests` target to trigger annotation explicitly.

### Proxy-app regression tests

Beyond the lit-driven `check-*` targets above, real proxy apps under
`data-race-detection-benchmark-suite/proxyApps/` are built/run as regression
tests in CI (`.gitlab-ci.yml`'s `apps` stage). There are two groups, and they
differ in kind — not just in which app they build.

**Build-only smoke tests** (`.proxyapp-make`/`.proxyapp-sh`). These build the
app and let `spmd-verify` print; they assert **nothing** about the result, and
run with `allow_failure: true`, so they only catch a broken build:

| CI job          | App subdir (under `proxyApps/`) | Invocation                     | Pass         |
|-----------------|---------------------------------|--------------------------------|--------------|
| `stencil`       | `PRK/MPIRMA/Stencil`            | `make stencil`                 | dataRace     |
| `stencil-shmem` | `PRK/SHMEM/Stencil`             | `make stencil`                 | dataRace     |
| `miniweather`   | `miniWeather/c/build`           | `bash cmake_claix_llvm_cpu.sh` | dataRace     |
| `tealeaf`       | `TeaLeaf`                       | `bash build.sh`                | dataRace     |

Note that `miniweather` and `tealeaf` here build the *non-OpenMP* variant of
their app (`make mpi` and `MODEL=serial` respectively), so despite sharing an
app name they do not overlap with the verification group below.

**Verification regression** (`.proxyapp-checks`). These are a **hard gate** —
no `allow_failure` — and each builds its app *twice*, asserting the outcome each
build must produce:

| CI job                | App subdir (under `proxyApps/`) | Build script            | Thread level | `correct` checks             |
|-----------------------|---------------------------------|-------------------------|--------------|------------------------------|
| `miniweather-checks`  | `miniWeather/c/build`           | `build_mpi_omp.sh`      | funneled     | thread-safety, collectives   |
| `tealeaf-checks`      | `TeaLeaf`                       | `buildOmp.sh`           | funneled     | thread-safety, collectives   |
| `hpgmg-checks`        | `hpgmg`                         | `build-wrapper.sh`      | multiple     | thread-safety only           |

The last column is the job's `PROXYAPP_CORRECT_CHECKS` variable, which the
`.proxyapp-checks` template passes to the `correct` build; it defaults to
`"thread-safety collectives"`. `hpgmg-checks` drops `collectives` because
check-collectives currently reports five false positives on HPGMG-FV — see the
comment above that job in `.gitlab-ci.yml` for the two causes (an `exit(0)`
malloc-failure guard whose condition is rank-non-uniform, and the OpenMP
lowering's own trip-count guard around each wsloop, which is thread-uniform by
construction but loaded from the heap-allocated `level` struct so
`UniformityAnalysis` cannot prove it). Those findings are not a regression to
chase: they only became visible once `ExecutionContextAnalysis` stopped leaving
every program point after the first `scf.for` uninitialized, which had made
HPGMG look clean vacuously. Dropping the single bad check keeps the job's two
thread-safety assertions as hard gates instead of making the whole job
`allow_failure`.

All three build scripts take the same positional arguments, handled by the
shared helper `proxyApps/proxyapp-common.sh` that each of them sources:

```
<build-script> [CONFIG] [CHECK ...]

  CONFIG  incorrect  build the app as published (default)
          correct    build with -DSPMD_FIX_THREAD_LEVEL
  CHECK   thread-safety  run check-thread-safety (default)
          collectives    run check-collectives
```

Nothing is passed in about the *expected* result — it is derived:

| Invocation                              | Expectation                        |
|-----------------------------------------|------------------------------------|
| `incorrect thread-safety`               | must report a violation (TP)       |
| `correct thread-safety`                 | must stay silent (TN)              |
| `collectives` (either config)           | must stay silent (TN)              |

Multiple `CHECK`s run against the same build, which is why CI gets three
results per app out of two invocations — `incorrect thread-safety`, then
`correct ${PROXYAPP_CORRECT_CHECKS}`. The thread-support level does not affect
collective matching, so `collectives` rides along with the `correct` build
rather than paying for a third one; `hpgmg-checks` is the one job that omits it
and so gets two results out of its two builds. Run one yourself with:

```sh
cd spmd/externals/data-race-detection-benchmark-suite/proxyApps/hpgmg
SPMD_WORKSPACE_DIR=$PWD/../../../.. bash build-wrapper.sh correct thread-safety collectives
```

(`--help` on any of the three prints the same contract.)

`SPMD_FIX_THREAD_LEVEL` guards exactly one `#ifdef` per app, at the
`MPI_Init`/`MPI_Init_thread` call:
`hpgmg/finite-volume/source/hpgmg-fv.c`, `TeaLeaf/driver/comms.cpp`,
`miniWeather/c/miniWeather_mpi_openmp.cpp`. For **TeaLeaf and miniWeather the
`incorrect` branch is the public source** (plain `MPI_Init`, i.e.
`MPI_THREAD_SINGLE`) — a pre-existing upstream bug, which is why the buggy
form is the default rather than the fix. For **HPGMG-FV**, which is built with
`-DUSE_MPI_THREAD_MULTIPLE=1` and therefore calls MPI from inside OpenMP
parallel regions, the `incorrect` branch is upstream's `MPI_THREAD_FUNNELED`
request that this build option outgrows. Editing these call sites (or a build
script's flags) by hand to switch configuration is what the arguments replace —
don't go back to it.

`proxyapp-common.sh` asserts on the same strings `litify.sh` puts in the CHECK
lines of the corresponding lit suites (`No thread-safety violations found` /
`warning: [CheckThreadSafety]`, `No Collective Communication Error Found` /
`warning: [CheckCollectives]`), and additionally **fails hard** if
`check-thread-safety` emitted `falling back to whole-module analysis` — that
fallback (a bitcode module with no `main`, from a broken toolchain or a bad
include path) would otherwise satisfy the true-positive expectation via its own
warning line and the true-negative one via an empty analysis, making both
directions pass for the wrong reason. `check-collectives` has no such fallback:
it calls `signalPassFailure()` and prints nothing, which the assertion catches
on its own.

Every proxy-app job runs with `SPMD_WORKSPACE_DIR` set to the `spmd/` checkout
and `PATH` pointing at the Bazel-built `install/bin`. `proxyApps/` also carries
several apps that aren't wired into CI at all (`sphexa`, `LULESH-RMA`,
`miniMD-RMA`, `miniVite`, `shorgpu`, `minq`, and the rest of `PRK/` —
`Transpose`/`Synch_p2p` across `MPIRMA`/`MPISHM`/`SHMEM`).

## Architecture

```
include/spmd/            SPMDDialect/Types/Ops/Attributes/Effects/Passes .td + generated headers (tablegen)
lib/spmd/                SPMDDialectLib: dialect, types, ops, attributes (.cpp)
lib/spmd/passes/         SPMDPassesLib — one cc_library per pass (see below)
lib/spmd/passes/CACTS/   Collective API Call Transformation System — per-programming-model transformers
lib/spmd/Analysis/       SPMDAnalysis — dataflow analyses passes are built on
lib/spmd/Utils/          PassUtils — shared pass helpers
spmd-opt/                spmd-opt.cpp — the mlir-opt-style driver binary
utility/                 spmd-verify.sh — source-to-verification wrapper, and `compile` back to an executable (genrule, path-substituted at build time);
                         check-setup.sh — which MPI/OpenSHMEM/NCCL/NVSHMEM runtimes a machine has;
                         run-clang-format.sh / run-buildifier.sh — the formatters CI gates on; git-hooks/ — the pre-commit hook (see utility/README.md)
includesProgramModels/   Per-model API JSON descriptions consumed by ConvertApiCallsToSPMD (mpi, shmem, nccl, mynvshmem, cuda, omp);
                         generated by USIS and copied in verbatim -- see its README.md
externals/                Benchmark suite submodules (data-race-detection-benchmark-suite, collective-verification-benchmark-suite)
test/                    lit unit tests (test/spmd/<area>/*.mlir, run by `bazel test //test:spmd_tests`);
                         the .c/.cpp files beside them are manual inputs, not collected;
                         test/exec/ — execution tests (lit, outside Bazel, needs MPICH and libomp)
```

New dialect ops/types/attributes go in `include/spmd/*.td` (tablegen) with
implementations in `lib/spmd/*.cpp`; new passes are declared in
`include/spmd/SPMDPasses.td` and implemented as a `cc_library` in
`lib/spmd/passes/BUILD.bazel`, then added to the `SPMDPassesLib` deps list.

Bazel is the only build system; there is no CMake build for `spmd/` (the two
`externals/` benchmark suites have their own). Because CI builds with
`--spawn_strategy=local`, actions are not sandboxed and a missing `deps` entry
does not fail the build -- when you add an `#include "spmd/..."`, add the
providing target to `deps` by hand.

### Pipeline / pass order

1. `omp-to-spmd` — lower OpenMP dialect structure to SPMD dialect (run before step 2; a canonicalization pass follows it to fold `spmd.getParallelComm`).
2. `convert-apiCalls-to-spmd` — lower per-model API calls (MPI/SHMEM/NCCL/NVSHMEM/CUDA/OMP, via CACTS transformers) into SPMD dialect ops.
3. Cleanup/normalization passes: `spmd-reconcile-unrealized-cast`, `convert-scf-switch-to-if`, `simplify-cmp-ops`, `convert-llvm-to-func`, `privatize-symbols`. Registered but deliberately **not** in `spmd-verify.sh`'s pipeline: `convert-arith-select-to-if`. It rewrites an if-converted fork (`spmd.allgather(arith.select %c, %commA, %commB, ...)`) back into an `scf.if` so the analyses see control flow, but it fires on every `arith.select` in the module and clones the using op — including region-carrying ops — into both arms. `CollectiveMismatchAnalysis::checkCommSelectFork` handles that shape directly on the value instead, with no IR mutation.
4. Verification passes (the actual analysis payload):
   - `check-dataRace` — static data-race detection (`--write-json-report` for JSON output).
   - `check-collectives` — static collective-communication mismatch detection (`--num-ranks`, `--write-json-report`).
   - `check-thread-safety` — verifies communication ops against the MPI-style thread-support level (SINGLE/FUNNELED/SERIALIZED/MULTIPLE) declared on the enclosing `spmd.parallel`'s `threadLevel` attribute; absence of the attribute defaults to SINGLE.

### Analyses (`lib/spmd/Analysis/`)

`UniformityAnalysis`, `HandleOriginsAnalysis`, `CommOriginsAnalysis`,
`PendingAccessAnalysis`, `ExecutionContextAnalysis`,
`CollectiveMismatchAnalysis`, `ParallelContextAnalysis` — the checker passes
above are built on top of these.

## Bazel output locations (don't browse recursively)

`bazel-bin`, `bazel-out`, `bazel-testlogs`, `bazel-spmd` here are symlinks
into `/tmp/$USER/bazelOut/...` (this project's `--output_base`, see
README/above for why it's redirected off the home directory). Never `Glob`
or `grep -r` through them: `bazel-spmd` is the execroot, a symlink farm
holding a *second copy* of the entire source tree plus `external/` with
~33 fetched deps (llvm-project, jax, protobuf, enzyme_ad, reactant) — so
an unscoped search returns every source hit twice, then recurses into
multi-GB of LLVM.

Targeted reads inside them are fine, and sometimes the only option:

- generated tablegen output, which exists nowhere else in the tree —
  `bazel-bin/include/spmd/SPMDOps.h.inc`, `SPMDAttributes.cpp.inc`,
  `SPMDPasses.h.inc`, etc. — when debugging a `.td` change;
- `bazel-testlogs/<target>/test.log` for a failing lit test (the path
  `bazel test` prints).

For "what targets/deps exist" questions, `bazel query` beats reading the
output tree. The `spmd-verify`/`spmd-opt` binaries under `bazel-bin/` are
meant to be invoked directly by name once built — e.g. as
`useful-scripts/` does — that's normal usage, not something to avoid.

`externals/` holds two git submodules that ARE real test corpora, not
vendor noise: `data-race-detection-benchmark-suite` and
`collective-verification-benchmark-suite`.

## LLVM/MLIR source: not vendored here, fetched transitively

LLVM is not checked out under `spmd/`. It's pulled in transitively:
`WORKSPACE.bazel` loads it from `@xla//third_party/llvm:workspace.bzl`
(via the Enzyme-JAX → XLA dependency chain), using `LLVM_TARGETS` from
`@enzyme_ad//:workspace.bzl`. Unlike Enzyme-JAX/Reactant (which expose
`OVERRIDE_ENZYME_JAX_PATH`/`OVERRIDE_REACTANT_PATH`), there is **no**
`OVERRIDE_LLVM_PATH`-equivalent — pointing Bazel at a local LLVM checkout
would require patching the `llvm_configure(...)` call in `WORKSPACE.bazel`,
which hasn't been done. The exact pinned commit isn't visible in this
project's own files: it is `LLVM_COMMIT` in XLA's
`third_party/llvm/workspace.bzl`, which after a build sits at
`/tmp/$USER/bazelOut/external/xla/third_party/llvm/workspace.bzl`. Read it
there; it moves with every Enzyme-JAX/XLA bump, so a SHA copied into any
document goes stale.

Where the workspace has a `../CLAUDE.md`, its "LLVM/MLIR reference clone"
section describes the reference-only local clone kept in sync with the real
resolved commit.

## Conventions

- **Formatting gate: run the formatters before every commit.** After editing
  any C/C++ or Bazel file, and before `git commit`, run

  ```sh
  ml GCCcore/14.2.0 LLVM/20.1.7
  utility/run-clang-format.sh          # or: ... run-clang-format.sh <file>
  utility/run-buildifier.sh            # only if BUILD.bazel/*.bzl changed
  ```

  and confirm with `utility/run-clang-format.sh --check`, which is byte for
  byte what CI runs. Do not commit unformatted code and leave CI to find it:
  `formatting` is a hard gate in the `compliance` stage, which now runs
  *before* `build`, so the whole pipeline stops there. Same standing
  requirement as the regression suites above.

  It is enforced by CI's `formatting` job, a hard gate covering two tools:
  - C/C++ against `.clang-format` (plain `BasedOnStyle: LLVM`). Run
    `utility/run-clang-format.sh` (`--check` for CI's exact check) with
    `ml GCCcore/14.2.0 LLVM/20.1.7` loaded -- the script requires clang-format
    20.x, since output differs between major versions. Exclusions are in
    `.clang-format-ignore` (`includesProgramModels/`, `test/`, `patches/`,
    `externals/`); `.td` files are never formatted (clang-format has no
    TableGen mode). Expect it to reorder `#include`s within a block -- that is
    correct behaviour, not a mistake to undo.
  - `BUILD.bazel`/`WORKSPACE.bazel`/`*.bzl` against buildifier 8.2.1. Run
    `utility/run-buildifier.sh` (`--check`, `--bootstrap` on first use since
    buildifier is not a module). Expect it to sort `srcs`/`deps` and reorder
    attributes into its canonical order.
  Both accept pathspecs. `utility/git-hooks/pre-commit` runs both over a
  commit's own files; enable with `git config core.hooksPath utility/git-hooks`.
- C++17, built via Bazel `cc_library`/`cc_binary`/`gentbl_cc_library`.
- Pass `.td` descriptions in this tree are frequently still placeholder text (`sample Text`) — don't treat a pass's tablegen `description` as authoritative; read the `.cpp` and the `SPMDPasses.td` comment above `CheckThreadSafety` (the one pass with a fully written-out spec) as the model for how a real description should read.
- Passes operate on `ModuleOp` unless noted otherwise (`privatize-symbols` runs on any op).
- Unsupported *input* is reported with `llvm::reportFatalUsageError`, not `llvm_unreachable`: the shipping build is `-c opt`, which defines NDEBUG, and `llvm_unreachable` then compiles to `__builtin_unreachable()` -- undefined behaviour with no message. `reportFatalUsageError` is always enabled, exits 1, and does not print a bogus "report an LLVM bug" trace. `llvm_unreachable` is reserved for exhaustive switches over closed enums; use `reportFatalInternalError` for a genuine internal invariant that must hold in release builds too.
- OpenMP support is a subset, and the lowered subset has modelling gaps (task scheduling order, `spmd.taskwait`, worksharing-loop uniformity). Both lists live at the top of `lib/spmd/passes/OMPToSPMD.cpp` -- that file, not this one, is the place to update them.
